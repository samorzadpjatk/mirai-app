# Testing Guide for @mirai-app/db

## Overview

This document explains the testing strategy for the `@mirai-app/db` package and why traditional unit tests are not implemented here.

## Why No Unit Tests?

The `@mirai-app/db` package is intentionally **excluded from unit testing** for the following reasons:

### 1. Package Responsibility

This package serves a single, focused purpose:
- **Prisma Schema Definition**: Defines the database schema using Prisma's declarative syntax
- **Prisma Client Export**: Re-exports the generated Prisma client for use by other packages
- **Migration Management**: Contains database migration files generated by Prisma

The package contains **no business logic** that would benefit from unit testing. It is purely a configuration and schema layer.

### 2. Prisma Client Characteristics

The Prisma client is:
- **Auto-generated** from the schema definition (in `src/prisma/lib/`)
- **Type-safe** by design - the generated client includes TypeScript types
- **Already tested** by the Prisma team with extensive test coverage
- **A thin wrapper** around database queries

Testing the Prisma client itself would be testing Prisma's implementation, not our code.

### 3. Testing Philosophy

```
┌─────────────────────────────────────────────────────────────┐
│                    Testing Pyramid                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ┌─────────────┐                                          │
│   │   E2E Tests │  ← Full application flows                 │
│   │  (minimal)  │                                          │
│   └──────┬──────┘                                          │
│          │                                                  │
│   ┌──────▼──────┐                                          │
│   │ Integration │  ← Database interactions tested HERE      │
│   │    Tests    │    in consuming packages (auth, trpc,     │
│   │             │    backend-server, etc.)                  │
│   └──────┬──────┘                                          │
│          │                                                  │
│   ┌──────▼──────┐                                          │
│   │   Unit      │  ← Business logic, utilities, services    │
│   │   Tests     │                                          │
│   │             │    @mirai-app/db: NOT NEEDED              │
│   └─────────────┘                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## Recommended Testing Approach

### Integration Tests in Consuming Packages

Database interactions should be tested through **integration tests** in the packages that consume `@mirai-app/db`:

| Package | Testing Approach | Rationale |
|---------|------------------|-----------|
| `packages/auth` | Integration tests with mocked Prisma | Test auth logic with controlled DB responses |
| `packages/trpc` | Integration tests with test database | Test router logic with real queries |
| `apps/backend-server` | Integration tests with test database | Test API endpoints end-to-end |
| `apps/seed` | Integration tests with mocked DB | Test seed logic without real DB writes |

### What to Test in Consuming Packages

When testing database interactions in other packages, focus on:

1. **Query Logic**: Verify that your queries return expected results
2. **Data Transformations**: Test mapping between Prisma models and domain objects
3. **Error Handling**: Verify behavior when database operations fail
4. **Transaction Behavior**: Test multi-operation consistency

### Example Integration Test Pattern

```typescript
// In packages/auth/src/__tests__/user-service.test.ts
import { prisma } from '@mirai-app/db';
import { createUser } from '../user-service';

describe('User Service', () => {
  beforeEach(async () => {
    // Clean up test data
    await prisma.user.deleteMany({ where: { email: { contains: '@test.com' } } });
  });

  afterAll(async () => {
    await prisma.$disconnect();
  });

  it('should create a user with valid data', async () => {
    const user = await createUser({
      email: 'test@example.com',
      name: 'Test User'
    });

    expect(user.email).toBe('test@example.com');
    expect(user.id).toBeDefined();
  });
});
```

## Schema Validation

While unit tests are not needed, the following validation is performed:

### 1. Prisma Schema Validation

```bash
# Validates schema syntax and generates client
cd packages/db && bun run db:generate
```

### 2. Migration Integrity

```bash
# Ensures migrations are valid and can be applied
cd packages/db && bun run db:migrate
```

### 3. Type Safety

```bash
# TypeScript compilation ensures generated client types are correct
cd packages/db && bun run typecheck
```

## When to Add Tests Here

Unit tests in `@mirai-app/db` would only be necessary if:

1. **Custom client extensions** are added (e.g., custom query middleware)
2. **Schema utilities** are implemented (e.g., schema validation helpers)
3. **Migration helpers** are created (e.g., custom migration scripts)

Currently, none of these apply, so the package remains test-free by design.

## Summary

| Aspect | Approach |
|--------|----------|
| Unit Tests | **Not needed** - no business logic to test |
| Integration Tests | **In consuming packages** - test DB interactions where they occur |
| Schema Validation | **Prisma CLI** - `db:generate`, `db:migrate` |
| Type Safety | **TypeScript** - `typecheck` script |

For questions about testing database interactions, refer to the testing documentation in the consuming packages where the actual business logic resides.

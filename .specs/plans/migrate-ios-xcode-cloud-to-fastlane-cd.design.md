## Context

iOS delivery currently depends on Xcode Cloud-managed build and submission jobs. The target state moves iOS build and App Store/TestFlight submission into repository-managed Fastlane lanes so release logic, validation, and operational runbooks are handled the same way as Android CD. The implementation must preserve key EAS Build iOS semantics from Expo documentation (`https://docs.expo.dev/build-reference/ios-builds/`) so the resulting pipeline keeps expected preflight, credential restore, native prep, and `gym` archive behavior. This change impacts CI workflow definitions, signing/authentication setup, and release operations for iOS maintainers.

## Goals / Non-Goals

**Goals:**

- Provide repeatable Fastlane lanes for iOS build and iOS submit that run non-interactively in CI.
- Align iOS CD structure with Android conventions for lane composition, preflight validation, artifact handoff, and failure behavior.
- Preserve EAS Build iOS operational expectations (credential handling, install/build lifecycle order, and artifact export conventions) while running in repository-owned CI.
- Define explicit secret and configuration contracts for App Store Connect auth, code signing, and lane inputs.
- Provide migration and rollback guidance for safe cutover from Xcode Cloud to Fastlane.

**Non-Goals:**

- Rewriting iOS application runtime features.
- Redesigning Android release logic or track policy.
- Introducing additional release tooling outside Fastlane and CI workflow primitives.

## Decisions

1. Use split lanes (`ios_build`, `ios_submit`, and orchestrating `ios_release`) instead of one monolithic release lane.
   - Rationale: supports submit-only reruns, clearer pipeline observability, and easier failure recovery.
   - Alternative considered: single lane that always builds and submits; rejected due to reduced operational flexibility.

2. Move all iOS release orchestration from Xcode Cloud into repository Fastlane files and CI workflow steps.
   - Rationale: keeps release behavior versioned, reviewable, and consistent with Android workflow ownership.
   - Alternative considered: hybrid Xcode Cloud + Fastlane; rejected because split ownership creates drift and unclear source of truth.

3. Define preflight validation for required credentials, signing assets, app identifiers, and lane parameters before any build/upload action.
   - Rationale: fail fast on misconfiguration, reducing wasted macOS runner time and partial releases.
   - Alternative considered: rely on downstream `gym`/`pilot` failure output only; rejected due to slower feedback loops.

4. Enforce explicit build-to-submit artifact handoff.
   - Rationale: submit-only runs must reference the exact IPA generated by the build stage, not a guessed default path.
   - Alternative considered: infer artifact from static path conventions; rejected because output names can vary by versioning/export options.

5. Keep iOS release logic Ruby-native in Fastlane (`Fastfile`/`Appfile`) with no Xcode Cloud runtime dependency.
   - Rationale: minimizes release toolchain complexity and mirrors Android Fastlane operational model.
   - Alternative considered: shell/Node helper scripts for release-critical behavior; rejected to avoid cross-runtime drift.

6. Model the iOS build lane after EAS Build iOS step ordering from Expo docs.
   - Rationale: teams already rely on EAS-compatible behavior such as fresh build context checks, credential restore, managed-project prebuild, pod install, optional lifecycle scripts, and `fastlane gym` output conventions.
   - Alternative considered: minimal custom Fastlane flow with only `gym` and `pilot`; rejected because it risks subtle regressions in build reproducibility and artifacts.

7. Route iOS submission target from SemVer bump level using Android-aligned policy.
   - Rationale: keeps release intent consistent across platforms and avoids per-run manual routing drift.
   - Policy: `patch` -> TestFlight internal testing, `minor` -> TestFlight external testing, `major` -> App Store distribution.
   - Alternative considered: manual destination selection at dispatch time; rejected because it is error-prone and bypasses SemVer governance.

8. Standardize secret materialization format for iOS signing inputs in CI.
   - Rationale: build lane must receive deterministic filesystem inputs while keeping secrets out of VCS.
   - Contract:
     - `credentials/ios/profile.mobileprovision` SHALL be materialized from `IOS_PROVISIONING_PROFILE_BASE64` environment secret (base64-encoded .mobileprovision file)
     - `credentials/ios/dist-cert.p12` SHALL be materialized from `IOS_DISTRIBUTION_CERTIFICATE_BASE64` environment secret (base64-encoded .p12 file)
     - `credentials.json` SHALL be materialized from plain-text secret inputs and MUST include:
       - `ios.distributionCertificate.path`: relative path to distribution certificate (e.g., `credentials/ios/dist-cert.p12`)
       - `ios.distributionCertificate.password`: plain-text password for the distribution certificate
       - `ios.provisioningProfilePath`: relative path to provisioning profile (e.g., `credentials/ios/profile.mobileprovision`)
     - The `bootstrap_ios_release_env!` function in Fastfile reads `credentials.json` and sets environment variables (`IOS_DIST_CERT_PATH`, `IOS_PROFILE_PATH`, `IOS_DIST_CERT_PASSWORD`) that are consumed during signing material preparation
   - Alternative considered: storing signing files directly in repository; rejected due to credential exposure risk.

9. Enforce archive-time distribution signing regardless of legacy Xcode project defaults.
   - Rationale: Xcode archive can still request development certificates when project-level settings drift (for example, `Apple Development` or `iPhone Developer` in Release), even if export options are distribution-oriented.
   - Contract:
     - Fastlane MUST apply provisioning profile UUID to the Xcode project before `gym`.
     - Fastlane MUST pass explicit archive signing overrides (`CODE_SIGN_STYLE=Manual`, `CODE_SIGN_IDENTITY=Apple Distribution`, `DEVELOPMENT_TEAM=<profile team>`) to `xcodebuild` via `gym` `xcargs`.
   - Alternative considered: relying only on `export_options.provisioningProfiles`; rejected because it does not control archive-time signing identity selection.

## Risks / Trade-offs

- [App Store Connect auth or permission misconfiguration] -> Mitigation: strict preflight checks for API key variables/roles and actionable failure messages.
- [Code signing material mismatch on CI runner] -> Mitigation: validate certificates/profiles/team/bundle identifiers before invoking build lane.
- [Archive requests development certificate despite release destination] -> Mitigation: enforce archive-time manual distribution signing overrides and project provisioning update before `gym`.
- [IPA not found during submit-only execution] -> Mitigation: pass explicit artifact path from build outputs and validate existence before upload.
- [Behavior drift from EAS iOS defaults breaks existing assumptions] -> Mitigation: codify EAS parity checklist and verify lane step order against Expo build-reference during rollout.
- [Wrong release audience due to misrouted destination] -> Mitigation: derive destination from SemVer bump type and log resolved route in CI before submit.
- [Operational learning curve after Xcode Cloud removal] -> Mitigation: lane-level runbook updates and rollback instructions for first release window.
- [Longer setup on macOS CI than managed cloud defaults] -> Mitigation: pin tool versions and document bootstrap steps in workflow.

## Migration Plan

1. Introduce iOS Fastlane lanes and CI workflow in parallel with existing Xcode Cloud release path.
2. Add preflight validation and EAS-parity checks (credentials, install order, prebuild/pods, gym/archive path behavior).
3. Implement SemVer destination routing and secret materialization contract in workflow preflight.
4. Run at least one side-by-side release rehearsal to compare Fastlane outputs against current iOS release expectations.
5. Validate patch/minor/major rehearsal routing outcomes (`internal` TestFlight, `external` TestFlight, App Store).
6. Switch primary iOS CD trigger to Fastlane workflow and disable Xcode Cloud release trigger.
7. Monitor first production rollout with heightened verification checks and on-call support.

Rollback strategy:

- Keep Xcode Cloud workflow configuration available for one release window.
- If Fastlane release fails critical validation, re-enable Xcode Cloud trigger and restore prior secret mapping while issues are addressed.

## Open Questions

- Are existing signing assets already CI-exportable, or do we need one-time certificate/profile re-export before cutover?
- Do we require branch-specific iOS release channels at launch, or a single mainline release path first?

Resolved rollout policy:

- `patch` releases route to TestFlight internal testing.
- `minor` releases route to TestFlight external testing.
- `major` releases route to App Store distribution.

## Initial User Prompt

I want to replace the SupabaseStorageGateway with StorageGateway based on MinIO and tusd - check if that's possible, if not what are other alternatives to Supabase

## Description

This feature implements a self-hosted file storage solution to replace the Supabase Storage dependency, providing vendor independence and cost reduction while maintaining full compatibility with existing file upload and download workflows.

**Key Discovery:** MinIO was archived in February 2026. The solution uses **SeaweedFS** as the S3-compatible object storage server instead, with **tusd** as the resumable upload server. Authentication is handled via a ticket-based system using Redis, where upload tickets are generated by the backend, stored in Redis with time-to-live (TTL), and validated by tusd via webhooks before allowing file transfers.

**Key capabilities delivered:**
1. **Resumable Uploads**: Users can upload large files (up to 100MB) that automatically resume if network connections are interrupted, critical for mobile users on unreliable networks.
2. **Secure Authentication**: Upload tickets are single-use, expire after 1 hour, and are scoped to specific users and buckets, preventing unauthorized access.
3. **Direct Downloads**: Files are served via time-limited presigned URLs (15-minute expiration) for secure access, with public bucket support for unauthenticated assets.
4. **Clean Architecture Compliance**: The SeaweedFSStorageGateway implements the existing IStoragePort interface without changes, ensuring all use cases continue to work without modification.
5. **Developer Experience**: Docker Compose configuration provides local development environment with SeaweedFS, tusd, and Redis running locally.

**Constraints:**
- All implementations must follow Effect patterns (Effect.Effect<T, IPortError, never>)
- IStoragePort interface cannot change (existing contract)
- Mobile app must work without code changes (endpoint URL only)
- Both SeaweedFS and Supabase gateways must coexist during migration

## Architecture Overview

### Solution Strategy

The architecture follows the **Adapter Pattern** within Clean Architecture, replacing the SupabaseStorageGateway implementation while preserving the domain contract. The solution consists of three primary components:

1. **SeaweedFS** - S3-compatible object storage (replaces MinIO after archival discovery)
2. **tusd** - Resumable upload server handling the tus protocol
3. **Redis** - Ticket state management for upload authentication

**Approach:** Implement a new gateway adapter (`SeaweedFSStorageGateway`) that implements the existing `IStoragePort` interface. Use a configuration-based factory to select between Supabase and SeaweedFS implementations at runtime, enabling zero-downtime migration.

**Key Reasoning:**
- **SeaweedFS over MinIO:** MinIO was archived Feb 2026; SeaweedFS is actively maintained with Apache 2.0 license
- **tusd over custom implementation:** tus protocol is battle-tested; tusd handles edge cases (network interruption, chunking, checksums)
- **Redis for tickets:** Provides TTL expiration natively, high-performance lookups, and simple single-use enforcement
- **Clean Architecture preservation:** Zero changes to domain layer or use cases; only adapter layer affected

### Key Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Object Storage | **SeaweedFS** | Active maintenance, S3-compatible, O(1) disk access |
| Upload Protocol | **tusd** | Industry-standard tus protocol, resumable uploads |
| Auth State | **Redis** | Native TTL, fast lookups, simple single-use tokens |
| Migration Strategy | **Parallel gateways** | Config-based selection allows gradual cutover |
| Interface Changes | **None** | IStoragePort contract preserved |

### Contracts

**IStoragePort Interface (Unchanged):**
```typescript
export interface IStoragePort {
  upload(
    bucket: string,
    path: string,
    file: File | Blob,
  ): Effect.Effect<{ path: string; publicUrl: string | null }, IPortError, never>;

  download(
    bucket: string,
    path: string,
  ): Effect.Effect<Blob, IPortError, never>;

  getPublicUrl(bucket: string, path: string): string;

  delete(bucket: string, path: string): Effect.Effect<void, IPortError, never>;

  list(
    bucket: string,
    path?: string,
  ): Effect.Effect<string[], IPortError, never>;

  createSignedUploadUrl(
    input: CreateSignedUploadUrlInput,
  ): Effect.Effect<CreateSignedUploadUrlResult, IPortError, never>;

  createSignedDownloadUrl(
    input: CreateSignedDownloadUrlInput,
  ): Effect.Effect<CreateSignedDownloadUrlResult, IPortError, never>;
}
```

**UploadTicket Type:**
```typescript
interface UploadTicket {
  token: string;           // UUID v4
  userId: string;          // Owner
  bucket: string;          // Target bucket
  path: string;           // Object key
  expiresAt: Date;        // TTL (1 hour)
  used: boolean;          // Single-use flag
}
```

**TusHookPayload (Webhook):**
```typescript
interface TusHookPayload {
  Type: 'pre-create' | 'post-finish' | 'post-terminate';
  Event: {
    Upload: {
      ID: string;
      Size: number;
      MetaData: { filename: string; userId: string; token: string };
    };
    HTTPRequest: {
      Header: Record<string, string[]>;
    };
  };
}
```

**Pre-create Hook Response:**
```typescript
// Success - allow upload
{ ChangeFileInfo: { ID: string; MetaData: object } }

// Failure - reject upload
{ HTTPResponse: { StatusCode: 401 }, RejectUpload: true }
```

## Execution Directive

### Sub-Agent Execution Model

Sub-agents execute in **waves** with maximum parallelization within each wave. The orchestration follows these rules:

1. **Wave Gates:** All steps in a wave must complete before starting the next wave
2. **Dependency Blocking:** Steps with "dependencies" must wait for those steps to finish
3. **Parallel Execution:** Steps with "parallel with" can execute simultaneously
4. **Agent Selection:** Use the specified agent type for each step
5. **Quality Gates:** Each step requires `/sadd:judge` verification before wave completion

### Wave Structure

| Wave | Steps | Trigger Condition | Parallel Agents |
|------|-------|-------------------|-----------------|
| Wave 1 | 1.1, 1.2, 1.3, 2.1, 2.3 | Task start | 5 |
| Wave 2 | 2.2, 3.2 | Wave 1 complete | 2 |
| Wave 3 | 3.1, 3.3 | Wave 2 complete | 2 |
| Wave 4 | 3.4, 4.1 | Wave 3 complete | 2 |
| Wave 5 | 4.2, 4.3, 4.5 | Wave 4 complete | 3 |

### User Scenarios

**Primary Flow (Happy Path): Upload and Download**
1. **Given**: Authenticated user with valid session
2. **When**: User selects file to upload in mobile app
3. **Then**: App calls createUploadUrl GraphQL mutation
4. **And**: Backend generates upload ticket in Redis
5. **And**: Backend returns tusd endpoint + token to app
6. **And**: App uses tus-js-client to upload file with token
7. **And**: tusd validates token with Redis
8. **And**: File stored in MinIO
9. **And**: tusd calls post-finish webhook
10. **And**: Backend confirms upload completion
11. **When**: User wants to download file
12. **Then**: App calls createDownloadUrl GraphQL mutation
13. **And**: Backend generates presigned URL
14. **And**: User downloads file from MinIO

**Alternative Flow: Resumable Upload After Interruption**
1. **Given**: User started 50MB upload, network interrupted at 30MB
2. **When**: Network connection restored
3. **Then**: tus-js-client automatically resumes from 30MB
4. **And**: Upload completes successfully

**Error Handling Scenarios**
- Expired upload ticket: tusd rejects with 401, app requests new URL
- File not found: System returns FileNotFoundError
- Redis unavailable: System returns ServiceUnavailableError
- Invalid token: tusd rejects upload with 401

## Acceptance Criteria

### Functional Requirements

- [ ] **FR-1: Upload URL Creation**
  - Given: Authenticated user with valid session
  - When: createSignedUploadUrl is called with bucket and path
  - Then: Upload ticket created in Redis with 1-hour TTL
  - And: Returns tusd endpoint URL and authentication token

- [ ] **FR-2: Resumable File Upload**
  - Given: Valid upload ticket in Redis
  - When: tus-js-client uploads file to tusd endpoint with token
  - Then: tusd validates ticket via pre-create hook
  - And: File stored in MinIO bucket at specified path
  - And: tusd calls post-finish webhook

- [ ] **FR-3: Presigned Download URL**
  - Given: File exists in MinIO at bucket/path
  - When: createSignedDownloadUrl called with expiration seconds
  - Then: Returns presigned URL valid for specified duration
  - And: URL provides direct access to file in MinIO

- [ ] **FR-4: File Listing**
  - Given: Files exist in bucket with specified prefix
  - When: list(bucket, prefix) called
  - Then: Returns array of file paths matching prefix

- [ ] **FR-5: File Deletion**
  - Given: File exists in MinIO at bucket/path
  - When: delete(bucket, path) called
  - Then: File removed from MinIO
  - And: Subsequent access returns FileNotFoundError

- [ ] **FR-6: Public URL Generation**
  - Given: File exists in public bucket
  - When: getPublicUrl(bucket, path) called
  - Then: Returns direct MinIO URL without expiration

- [ ] **FR-7: Ticket Expiration**
  - Given: Upload ticket expired (TTL passed)
  - When: tusd validates expired token
  - Then: Returns 401 Unauthorized
  - And: Upload is rejected

- [ ] **FR-8: Single-Use Ticket Enforcement**
  - Given: Ticket was already used for successful upload
  - When: Second upload attempt with same token
  - Then: Returns 401 Unauthorized
  - And: Upload is rejected

- [ ] **FR-9: Contract Test Compliance**
  - Given: MinIOStorageGateway and InMemoryStorageGateway implement IStoragePort
  - When: Contract tests execute
  - Then: Both implementations pass identical test suite

- [ ] **NFR-2: Security**: Upload tickets expire after 1 hour (3600 seconds); single-use only; scoped to user
- [ ] **NFR-3: Reliability**: Redis persists tickets until TTL or completion; tusd hooks implement retry logic
- [ ] **NFR-4: Compatibility**: tusd server compatible with existing tus-js-client library
